# 求解器设计

## 1. 文档目的与边界

本文负责说明当前规划模型、约束类别、任务状态、异步求解、终止、过程指标、结果后处理和结果应用。

本文不重复接口字段，不规定页面展示形式，也不把尚未启用的权重解释为新增需求。精确模型字段见 [`docs/openapi.yaml`](../openapi.yaml)。

## 2. 求解模型

* `RoutePlan` 是 OptaPlanner 的规划解，包含 Agent、Ticket、POI、仓库、矩阵、约束配置、成本参数和分数。
* `AgentEachDay` 是按日参与排程的规划实体，维护其 Ticket 链。
* Ticket 的 Agent 归属及在链中的顺序是求解器调整的主要内容。
* 到达时间由链结构、服务时长和在途时间派生，链变化后由变量监听器级联更新。
* pinned Ticket 保持既有指派或顺序，不参与相应移动。

## 3. 分数与约束体系

求解使用 `HardMediumSoftLongScore`：Hard 表示必须优先满足的可行性条件，Medium 表示次级业务偏好，Soft 表示优化目标。实际启用与权重取值由当前 `RoutePlanConstraintConfiguration` 决定。

当前约束按职责分为：

| 类别 | 当前覆盖内容 |
| --- | --- |
| Agent 能力 | 载重与体积容量、最大接单数、技能匹配、资质等级 |
| Ticket 时序 | 依赖顺序、依赖工单同 Agent、最晚完成、期望时间窗、计划日期 |
| 关联与网点 | 关联工单同 Agent、Agent 与工单同仓库/网点 |
| 成本目标 | 行驶时间、行驶距离、Agent 固定成本 |
| 均衡目标 | 工单量、容量使用率、工作时长均衡 |
| 稳定与兜底 | 减少既有指派变化、惩罚使用虚拟 Agent |

部分配置项当前权重为零。它们属于现有模型字段，但零权重表示当前默认配置不参与评分；不得仅因字段存在就宣称相应行为已强制执行。

## 4. 任务状态

| 状态 | 含义 |
| --- | --- |
| `SOLVING_SCHEDULED` | 任务已保存并提交给求解管理器，等待开始 |
| `SOLVING_ACTIVE` | 求解进行中，可能持续产生更优解和过程采样 |
| `SOLVING_FINISHED` | 正常结束，最终方案与说明已保存 |
| `NOT_SOLVING` | 当前未运行；也用于启动恢复时重置遗留运行态 |
| `ERROR` | 求解或后处理失败，异常信息已记录 |

任务历史可以包含多个状态记录，但任何时刻只允许一个任务处于调度中或求解中。“当前任务”是任务索引指向的最新任务。

## 5. 异步求解流程

1. 启动前验证当前场景、POI 和矩阵是否完整，验证求解时长格式，并拒绝并发启动。
2. 对规划解初始化，保留需要固定的既有路线信息。
3. 创建任务标识和时间信息，将调度中状态先写入任务仓库。
4. 通过 `SolverManager.solveAndListen` 异步启动求解。
5. Best Solution 回调为严格更优的方案追加指标；等分方案可刷新任务方案但不重复追加等价指标，分数回退的候选不覆盖已记录最佳方案。
6. 独立采样记录搜索过程，不携带 `RoutePlan`，避免采样写入覆盖方案。
7. 正常结束时根据 `draw_route` 选择后处理：为真时补充已有路线，为假时补充变更工单相关矩阵数据；随后生成分数解释、最终指标和完成状态。
8. 失败时记录 `ERROR` 和异常对象；配置了回调时发送失败结果。当前异常对象可能包含内部堆栈，边界见[安全说明](./security.md)。

## 6. 终止规则

* 请求的求解时长短于 Solver 配置上限时，服务会安排提前终止。
* 显式终止只对调度中或求解中的任务有效。
* 终止操作交给 `SolverManager`，随后读取任务的持久化状态。
* 正在运行的任务不能直接删除。
* 应用启动时，磁盘中遗留的调度中或求解中状态会被重置为 `NOT_SOLVING`；进程重启不会继续原求解计算。

## 7. 过程指标

`SolutionMetrics` 记录三类采样：

* `BEST_SOLUTION`：产生并接受更优方案时记录。
* `SEARCH_SAMPLE`：求解活跃期间的搜索采样，写入频率最多每秒一次。
* `FINAL_SOLUTION`：任务正常完成时记录。

指标用于任务详情中的分数过程和求解进度展示，不作为独立任务状态源；任务状态以 `SolverJob.status` 为准。

## 8. 结果后处理与应用

* 求解输入要求 POI 和场景矩阵在任务启动前已完整构建；任务提交时的 `matrix_mode` 与 `build_transit_matrix` 当前只写入任务元数据并用于列表筛选，不会在求解阶段重新构建输入矩阵。
* 当前最终方案后处理只按 `draw_route` 分支：为真时补充路线展示数据，为假时补充变更工单相关的矩阵数据。
* 最终分数说明写入任务，供接口和控制台展示。
* 发送回调时会移除在途矩阵；REST/MCP 的响应边界分别见[接口说明](../interfaces/api.md)和 [MCP 参考](../reference/mcp.md)。
* 应用结果时以当前场景为目标，先验证 Agent、Ticket 等对象集合兼容，再把任务方案写回；验证失败不修改场景。
* 按产品约束只应应用已停止任务；当前门面应用路径尚未显式检查任务状态，因此实现仍可能接受运行中任务的已有方案，这属于待收敛的实现缺口而非受支持能力。

## 9. 非目标

本文不定义当前异步求解生命周期之外的调度、恢复或调参能力，也不新增约束。
